## Unreleased

Merged to `master` and not yet published. Nothing below resolves from Maven Central
yet; the current release is still 2.4.0.

Fixes from an external review of the SDK. Every finding was re-verified against the
code and the vendors' own documentation before being accepted, and each fix ships with a
regression test that fails without it. One additive API; nothing existing changed or was
removed.

### Added

**`AdManager.updateGlobalRequestConfiguration()` — change request configuration at runtime.** `initialize()` treats its entire configuration as process identity, so a second call with a different content rating, age treatment, personalisation state or even ad volume returned `INITIALIZATION_CONFLICT` and told the publisher to restart the process. That is correct for the app ID, which the platform SDK cannot be told twice, but not for request configuration: Android exposes `MobileAds.setRequestConfiguration()` and iOS a mutable `requestConfiguration`, both intended for runtime use. An app switching to a profile that needs different ad treatment now has a supported path. Inventory loaded under the previous policy is dropped when a serving-relevant field changes, and kept when only audio or test devices do; `initialize()` keeps its existing conflict semantics unchanged.

### Fixes

**Android banner terminal callbacks no longer touch the `AdView` off the main thread.** GMA Next-Gen delivers ad callbacks on a background pool, and the Next-Gen reference marks `AdView.unregisterBannerAd()` and `AdView.destroy()` `@MainThread`. Both callbacks called them inline on the callback thread, on the ordinary load path — entering `Dispatchers.Main.immediate` before registering a callback does not change the thread the SDK invokes it on. The whole settle transaction now runs in one posted Main block.

**A duplicate `onAdLoaded` no longer destroys the banner that was just admitted.** The success callback still guarded with `isActive` and destroyed the view unconditionally when it read false, so a second terminal callback for one request tore down the live banner. One owner now decides, on Main, which callback takes the view; every later one returns without touching it.

**A `Fixed` banner requests the width it was configured with.** In both platform size mappers the `widthDp` function parameter shadowed `AdSizePolicy.Fixed.widthDp`, so a `Fixed(320, 50)` placement in a 400dp container was requested as 400x50 — a non-standard size, from a policy whose entire purpose is to be fixed. `heightDp` was unaffected, which is what made the result a plausible-looking hybrid. The iOS characterization test passed 320 as both the configured and the container width, so it could not see the difference; it now passes different values.

**iOS applies `publisherFirstPartyIdEnabled`.** It was logged as "Ad Manager only" and dropped. `-[GADRequestConfiguration setPublisherFirstPartyIDEnabled:]` is part of the AdMob iOS surface, and Google documents the key as enabled by default and persisted across app sessions — so the value silently discarded was `false`, the only one a publisher has a reason to set.

**A banner refresh no longer stops after landing mid-load.** The refresh loop waited on `snapshotFlow { controller.loadState.value !is Loading }`. `snapshotFlow` re-runs only when a Compose `State` read inside it changes, and a `StateFlow`'s `value` is not one, so if the first read said `Loading` nothing could ever wake it and that banner stopped refreshing for the lifetime of the effect. It now collects the flow, and re-checks foreground and on-screen visibility after the wait.

**Changing a banner's explicit `widthDp` no longer blanks it.** The mirrored banner state was keyed on the width while the coroutine writing it was keyed only on the controller, so a width change created a fresh empty state that nothing ever wrote to again. Both are now keyed on the controller.

**A blank ad attribution badge is reported instead of accepted.** The layout validator recorded attribution by node type, so an `AdBadge` whose text resolved to empty — a missing localization, say — satisfied both the "has a badge" and the "badge is at the top" checks while rendering nothing. Google requires visible ad attribution, so a blank badge now warns and counts for neither check. Static text already had this check.

**A cancelled app-open show no longer blocks every full-screen format.** Admission took the process-wide presentation token and then launched the coroutine whose `finally` releases it. A coroutine cancelled before its first dispatch never runs its body, so a `stop()` or scope cancellation in that window stranded the token for the rest of the process, silently preventing interstitial, rewarded and app-open ads from ever presenting again. Admission now happens inside the launched coroutine.

**A native ad session created before initialization finishes now loads.** Dormant sessions exist so a feed can be built while `initialize()` is still running; on acceptance their windows are replayed, which schedules demand immediately. But `status` was published as `Ready` only after the `AfterMobileAdsInitialize` hooks, so that demand hit a closed request gate, the refusal was recorded as a non-retryable slot error, and demand reconciliation deliberately skips a slot that has one. The first screen's native ads stayed `Failed` despite a successful initialization, until the row scrolled away and back. `Ready` is now published before native sessions are configured.

**An initialization hook can await `Ready` or load an ad.** Same root cause, seen from the hook's side: `Ready` was published after the hooks ran, so a hook that waited for it waited forever. Anything that must precede every ad request still belongs in `BeforeMobileAdsInitialize` — the trade-off of publishing earlier is that a request elsewhere in the app may begin while an `After` hook is still running, which the hook documentation now states.

**Calling `initialize()` from inside a hook no longer deadlocks.** The nested call was admitted as a follower of the attempt that is waiting for the hook to return, with no timeout anywhere in that path. It now returns the manager's current status. Detection uses a coroutine-context marker, so it covers a nested call that inherits the hook's context, not one dispatched into an unrelated scope — the hook documentation says so explicitly.

**A concurrent `initialize()` no longer reports `Ready` for a native memory policy it did not install.** The native ad memory policy is deliberately not part of the GMA initialization identity, but a follower joining an in-flight attempt short-circuited on that identity alone and returned the leader's `Ready`. The identical call made after initialization settled returned `INITIALIZATION_CONFLICT`: the same request got a different answer depending only on timing. Followers are now reconciled against the full configuration.

**iOS native ad text scales with Dynamic Type.** The renderer set `adjustsFontForContentSizeCategory` on every label, but Apple documents that flag as effective only for a font obtained through `UIFontMetrics` or `preferredFont(forTextStyle:)` — and every font it built was a fixed-size system font, so the flag did nothing. A user with larger text saw the app around the ad grow while the ad's own headline, body, attribution and call-to-action stayed put. Android was never affected: it assigns `textSize` in `sp`, which the platform scales. The field is named `fontSizeSp`, so scaling is the behaviour it already promised on both platforms. Fonts are now scaled once, in the renderer, which also covers the custom-font path. **Worth re-checking your layouts at large text sizes**: ad copy that never grew before now does, so a fixed-height template has less room than it used to.

**Memory-pressure trimming is actually connected.** The documentation has always said native inventory is trimmed when the system asks for memory, and both platform signals existed and were unit-tested — but nothing ever constructed them outside tests, so no trim ever reached the coordinator. They are now registered when native ads are configured. The defect that would have made this harmful, a trim stranding an in-flight load, is fixed in the same release and had to land first.

**An automatic reload no longer destroys the rewarded ad kept for a late reward.** A successfully shown rewarded ad is deliberately retained after dismissal so a mediated reward callback arriving late still has its ad. But `reloadAfterShow` schedules a load on that same dismissal, and the next load drained every retained ad unconditionally — so with both enabled, the retention lasted milliseconds. Retained ads now survive a short grace period, and only an ordinary load after it retires them; `clear()` still drains immediately. Google's iOS guidance is that the reward normally precedes dismissal but that a mediation adapter decides its own ordering, which is the case this retention exists for. No test covered the combination: the retention tests leave `reloadAfterShow` off, and the reload tests use a format that never retains.

**A native ad view cannot render an ad that has been replaced underneath it.** The renderer lease was cached for as long as its composable lived, keyed on session, slot, placement and renderer — none of which change when the slot's record is replaced — and the published slot states carry no record identity to notice the swap. The lease is now re-validated on each read, and a stale one is released rather than served. No live failure was demonstrated for this; it is defence in depth.

**A layout tree can no longer change after it has been validated.** `AdLayout` computes its identity and validation report once, but a container kept whatever `List` it was handed — and in Kotlin a `List` is read-only, not immutable, so passing a `MutableList` is silent and idiomatic. Editing that list afterwards left a layout whose cached report described a tree that no longer existed. The tree is now snapshotted at construction, and validation and both renderers read the snapshot.

**The UMP iOS framework is fetched from a versioned URL instead of a rolling one.** Every UMP version resolved to the same `googleusermessagingplatform.zip`, which always serves the current release — so the checksum pinned inside an already-published plugin version would stop matching the day Google refreshed that file, breaking every consumer with a cold cache and no way to recover but overriding the digest by hand. Google publishes a versioned, content-addressed artifact for its own Swift package; the plugin now uses it, with Google's published checksum. The two archives are laid out differently — the rolling one wraps the framework in a version directory, the versioned one does not — so extraction now handles both. The comment claiming Google does not version-pin UMP was wrong.

**The Gradle plugin recognises iOS targets by architecture, not by name.** It compared each Kotlin/Native target's name against `iosArm64` and `iosSimulatorArm64`, so a consumer who named a target anything else — which the Kotlin DSL allows — had it silently skipped, and its test executables reached the linker with no framework paths and failed with undefined `GAD*`/`UMP*` symbols pointing nowhere near the cause. Targets are now classified by their `konanTarget`, the downloads attach to each test binary's own link task rather than being matched by task-name substring, and an unsupported iOS target warns instead of disappearing.

**`--offline` is respected.** With a missing or damaged framework cache the download task opened a connection regardless, so an offline build waited on connect and read timeouts and then reported a network error that never mentioned offline mode. It now fails immediately, naming the artifact it needs and how to prepare the cache. An intact framework is unaffected: it is up to date, so the task does not run at all.

**A loaded ad is no longer lost between the platform and the shared core.** Every platform load hands its ad back out of a `withContext` hop, and kotlinx documents two ways that value disappears: the dispatch back to a caller that has since been cancelled discards it, and a timeout firing as the block completes returns "no ad" with the ad already built. In both cases the SDK object existed, the platform's own cleanup had already run (from its side the hand-off succeeded), and nothing else referenced it. Full-screen, banner and native loads now hold the ad in a slot outside those boundaries and destroy whatever was never accepted. The native path is the one that mattered most: its coordinator runs on a background dispatcher while loads hop to the main thread, so every native batch crosses a real thread boundary on the way back.

**A cancelled Android sequential native batch destroys the ads it already collected.** Sequential is the default batching and the load timeout covers the whole batch, not each request, so a slow network reaches this on ordinary traffic. Each request only cleaned up its own pending ads, so ads from earlier requests in the same batch were neither delivered nor destroyed, and the platform's identity map kept a strong reference to each one for the life of the process.

**Cancelling an iOS native load now actually stops it.** The platform awaited a `CompletableDeferred`, and cancelling the coroutine that awaits a deferred does not cancel the deferred — so the invalidation hook never ran. The load kept accepting ads and kept issuing the next request in a sequential batch long after the coordinator had retired its reservations, with no owner to destroy the results. A batch that finished just as its caller was cancelled is now destroyed too. The existing tests cancelled the deferred directly, which is not what production does, so they passed throughout.

**A native ad slot denied capacity is now retried when capacity frees up.** A slot that lost the race for a reservation was marked deferred and dropped, and nothing re-offered it when another session later released its ads — demand was only ever reconsidered on a window update. A scrolling feed recovered by accident, because every scroll republishes a window; a single inline slot publishes its window exactly once, so it stayed empty for the whole life of the screen, with no error and nothing to retry. Freeing capacity now re-offers it to demand that is still wanted, once per event, and deliberately not after a memory trim (which exists to lower the footprint, not to refill it).

**Memory pressure during an in-flight native load no longer strands the slot.** The trim removed the reservation's ownership entry and then called the cancellation helper, which looks that entry up to find what to cancel — so it found nothing, the slot was never settled, and every later success, failure or timeout rejected the load as no longer live. The slot showed `Loading` permanently, and demand reconciliation skips a slot with a load in flight, so not even an identical window update could revive it. Note this path has no production caller yet; the trigger is wired up in a later change, and the defect is fixed first so it never ships live.

**A native load cancelled before it starts no longer wedges its placement.** A viewport change in the same frame that submitted a load can cancel that load's coroutine before its body ever runs, and a coroutine cancelled at that point never runs its body at all — so the handler that clears the in-flight marker never executed. The placement was then considered permanently busy and every later ad for it sat at `Loading` for the rest of the process.

**A stale `close()` can no longer destroy a replacement native session.** The generation-scoped overload checked the generation, released its lock, then closed by key alone, so a session created in the gap was torn down instead — leaving the consumer holding a handle to a session that had just been closed underneath it. Check and removal now happen in one critical section, as the sibling `updateWindow` and `deactivate` overloads already did.

**Deactivating a native session before its renderer detaches keeps the retained ad.** Deactivation picks anchor records to keep for the return visit, and marks them out-of-window; releasing a renderer treats out-of-window as "nothing wants this any more" and retires it. So the ad deactivation had just chosen to keep was destroyed whenever the renderer happened to be released afterwards — which the showcase's own Deactivate control does every time. Retention no longer depends on that ordering.

**`clear()` no longer discards a concurrent load's replay options.** It retired the replay snapshot after releasing the publication lock, so a load for the new generation could store its options in between and have them wiped, leaving `reloadAfterShow` to replay placement defaults instead. The retire now happens inside the same lock, before the new generation is published. The old comment claiming no public sequence could observe this was wrong: the state publication resumes an inline `loadState` observer, which is exactly that sequence.

### Also unreleased: native feed, reload replay, and iOS lifetime fixes

No public API change in this group: `admob-cmp-core.klib.api` and
`admob-cmp-compose.klib.api` are byte-identical to 2.4.0.

#### Fixes

**A native ad feed that changed without changing its item count now republishes its window.** A pull-to-refresh that returned the same number of rows, or a slot mapping that resolved asynchronously, left every ad row holding the pre-refresh slot keys and sitting on its loading placeholder until the reader scrolled far enough to change the measured index set. `slotAt` reads your feed's own Compose state, but it was applied outside the snapshot observer, so nothing tracked those reads — the only thing standing in for them was the lambda's identity, which held or not depending on whether Compose memoized it. The mapping is now resolved inside the observer, so the state it touches is tracked, and the deduplication key compares resolved slots by value instead of comparing lambdas by identity.

**`reloadAfterShow` replays the request options the placement was actually loaded with.** The automatic reload after a `show()` rebuilt its request from `placement.requestOptions`, silently discarding any `AdRequestOptions` the original `load()` was given — so a placement loaded with per-session targeting reloaded without it. This is the same defect `refresh()` had for banners before 1.1.0, now fixed the same way. A `load()` that returns early without issuing a request, because the cache is already full or consent has not been granted, is not a request and does not replace the replayed snapshot.

**An iOS native ad no longer retains itself through its own paid-event handler.** The handler captured the Kotlin object holding the `GADNativeAd` while being installed on that same ad, closing a cycle ARC cannot collect. The ad survived removal from the owner registry until the asynchronous teardown happened to clear the handler, and survived indefinitely if the ad was never destroyed.

**A Dynamic Type change no longer rebuilds an iOS native ad.** The prepared UIKit tree was rebuilt whenever the resolved `Density` changed, and Compose Multiplatform's iOS layer folds the preferred content size category into `Density.fontScale`. Every text-size change therefore destroyed the ad host and registered a fresh `GADNativeAdView` against the same ad — a visible flicker, and an impression the ad SDK may count twice. The tree now tracks screen scale only; Dynamic Type continues to be handled in place, by the labels restyling themselves and the host re-measuring.

<Aside type="caution" title="Correction">
That last sentence was wrong when it shipped. The labels set `adjustsFontForContentSizeCategory`, but Apple documents that flag as effective only for fonts built through `UIFontMetrics` or `preferredFont(forTextStyle:)` — and every font the iOS renderer built was a fixed-size system font, so nothing restyled itself and iOS ad copy never scaled at all. The decision to key the tree on screen scale rather than text size was still correct; the justification was not. Fonts are scaled through `UIFontMetrics` from the next release, which is what makes the in-place re-render real.
</Aside>

**The Gradle plugin recognises every `os.name` a macOS host reports.** Its host check missed `darwin` and `osx`, both of which Gradle's own `OperatingSystem` accepts. A miss dropped the GoogleMobileAds linker options from Kotlin/Native test executables on a machine that needed them, surfacing much later as `Undefined symbols ... _OBJC_CLASS_$_GADBannerView` with nothing pointing back at the check.

#### Behaviour changes

<Aside type="caution" title="Behaviour changes">
1. **`slotAt` is now invoked inside a Compose snapshot observer.** Any snapshot state it reads becomes a dependency of the feed's viewport pipeline, which is what makes a same-count refresh republish. Keep the lambda cheap and free of side effects: it is called for the measured indexes and for a bounded range either side of them, never across the whole feed. A lambda that only indexes into your feed model — the documented shape — needs no change.
2. **`reloadAfterShow` reloads now carry the last `load()`'s options** rather than the placement defaults. If you relied on the reload resetting targeting back to `placement.requestOptions`, call `clear()` and `load()` with the options you want instead.
</Aside>

## 2.4.0

### Toolchain and SDK versions

Kotlin 2.3.20 -> 2.4.20, Compose Multiplatform 1.11.1 -> 1.12.0, AGP 9.3.1 -> 9.4.0, Gradle 9.5.0 -> 9.7.1. Bound Google SDKs: Google Mobile Ads Next-Gen (Android) 1.3.0 -> 1.4.0, GoogleMobileAds (iOS) 13.7.0 -> 13.9.0, staying inside the `13.x` major the published cinterop bindings target. User Messaging Platform is unchanged on both platforms (Android 4.0.0, iOS 3.1.0), already the latest release of each.

The public API is unchanged. `admob-cmp-core.klib.api` and `admob-cmp-compose.klib.api` are byte-identical to 2.3.0 — this release adds and removes nothing from the frozen ABI.

<Aside type="caution" title="Cross-Kotlin-minor consumers on iOS">
`admob-cmp` publishes cinterop klibs, which the [compatibility matrix](/reference/compatibility/) documents as excluded from klib backward compatibility. Moving the compiled-against Kotlin minor from 2.3.20 to 2.4.20 is exactly the scenario that guarantee does not cover. If your project links `admob-cmp` from a Kotlin 2.3.x toolchain, verify your iOS link step before adopting 2.4.0 — it is not guaranteed to resolve the same way a plain (non-cinterop) klib would across a Kotlin minor version change.
</Aside>

## 2.3.0

### Fixes

**Initialization no longer strands the manager in a non-`Ready` state** when the caller that started it was cancelled after the native handoff. Previously that blocked every ad request while GMA was in fact initialized. Concurrent equivalent `initialize()` callers also no longer cancel each other.

**The native initialization watchdog no longer races GMA's own completion bound, on either platform.** GMA invokes its completion once the SDK and its mediation adapters finish *or* after its own 30-second bound — the same on Android (`MobileAds.initialize`) and iOS (`startWithCompletionHandler`). The wrapper's watchdog was set to that same 30 seconds, so a slow but ultimately successful mediation setup could be reported as an initialization failure. It now waits 40 seconds on both platforms.

**Two consent form callers queued behind a launch-time consent info update could both proceed**, so the second presented the moment the first was dismissed — into a preload slot UMP had just consumed, which both platforms report as a form error rather than a second form. A form operation now claims the form slot when it is called rather than when it reaches the front of the queue, so the second caller declines.

**A timed-out consent info update no longer blocks the retry that follows it.** The operation's pin is released when the wrapper declares it dead, instead of lingering and making the next `requestConsentInfoUpdate` — including the one `initialize(InitializeOnlyIfAlreadyAllowed)` performs — decline without contacting UMP.

**Consent errors now carry a usable `AdError.domain`.** Android's `FormError.ErrorCode` and iOS's `UMPRequestErrorCode` occupy the same `1..4` numeric range with different meanings, so `AdError.code` alone was ambiguous across platforms.

`resetConsentForDebug()` again declines while a consent form operation holds the form slot. iOS consent-form errors are now logged with parity to Android. `doctorIos` no longer reports a commented-out `GADApplicationIdentifier` as configured.

### Behaviour changes

<Aside type="caution" title="Behaviour changes">
Three changes affect what `ConsentStatus` your code sees. Admission (`canRequestAds`) is unchanged by all three — it still carries whatever the last completed refresh established, which is what [UMP's own guidance](https://developers.google.com/admob/android/privacy) says to check when a consent operation reports an error.

1. **A failed consent refresh now returns `Failed`** rather than the mapped native status, even when a previous session's admission still permits ads.
2. **`requestConsentInfoUpdate` can now return `Failed`** when it declines because another native consent operation is still outstanding. This busy error is returned to the declined caller and does not overwrite shared published status. It carries `AdErrorCode.CONSENT_OPERATION_IN_PROGRESS`. Wait for the existing operation to finish before retrying if the action is still needed.
3. **`gatherConsent` no longer presents a form after a *timed-out* refresh**, while it still presents one after a refresh that completed with an error.

A late UMP callback still reconciles privacy truth unconditionally — a revocation is never dropped — but a superseded callback cannot overwrite a newer operation's published status, while callback reconciliation still refreshes current native privacy/admission values. It remains a valid case for an operation to return or publish `Failed` while `canRequestAds` remains `true` (if a previous completed refresh permitted ads).
</Aside>

## What changed in 2.2.0?

A reliability release covering exception, timeout, and cancellation behaviour across consent,
configuration, and ad presentation.

### `initialize()` now reports a refused configuration

Once a configuration has been handed to the process-global ad SDK, a later `initialize()` with a
*different* `AdConfig` (a different app ID, `globalRequestConfiguration`, or `nativeAdMemoryPolicy`)
is refused deterministically rather than being reported as applied. Previously, a mismatched second
call logged a warning and returned the previously applied status (usually `Ready`), masking the fact
that its configuration was ignored and ads continued serving under the first app ID.

Such a call now returns `AdManagerStatus.Failed` with `retryable = false` and the new
`AdErrorCode.INITIALIZATION_CONFLICT`. Calling `initialize()` repeatedly with the *same* effective
configuration — including retrying after a native initialization timeout — is unaffected and
remains idempotent.

<Aside type="caution" title="Behaviour change">
If you branch on the result of a repeated `initialize()`, a configuration mismatch that used to look
like `Ready` now surfaces as a non-retryable failure. `AdManager.status` still reports the
configuration that *was* accepted, so a rejected call never interrupts ad serving for the rest of
the app.
</Aside>

### Consent operations are serialized

Concurrent consent operations no longer interleave or corrupt in-flight UMP state:

- `requestConsentInfoUpdate()` queues behind any active consent operation; `gatherConsent()` queues
  behind a bounded update but returns a failed `ConsentStatus` if another form is already presenting.
- `showPrivacyOptions()` and `resetConsentForDebug()` return `false` when a form-presenting
  operation holds the consent slot — two forms cannot stack, and resetting under a live form is
  incoherent. The slot is claimed when such an operation starts, so this also covers the window in
  which a `gatherConsent()` is still awaiting a host and running its bounded info update, before any
  form is visible. A `requestConsentInfoUpdate()` never claims the slot: these calls **wait** for it,
  so a user opening privacy settings during a launch-time consent *refresh* still gets the form
  rather than a spurious failure. Callers should retry once the in-flight operation finishes.
- Cancelling the coroutine that called `gatherConsent()` or `showPrivacyOptions()` no longer frees
  the form slot. Cancellation does not dismiss a form the user is looking at, so other consent
  operations — including `resetConsentForDebug()` — keep declining until that form's own UMP
  callback reports back.

### Late UMP consent callbacks reconcile privacy state

A UMP consent-information callback arriving after the SDK's bounded timeout still reconciles
`canRequestAds` and `privacyOptionsRequirementStatus` with the latest native truth. If a user's
consent was revoked while a slow update was in flight, the late callback ensures the ad-request gate
closes and cached inventory is purged, rather than leaving obsolete permission active until the next
cold start.

### Per-presentation ad audio is restored more correctly

- The mute/volume override supplied to `show()` is no longer reverted when the **caller** cancels
  `show()` while the ad is still on screen. Restoration now happens when the ad actually closes.
- On Android, dismissing an ad restores the audio state configured through
  `globalRequestConfiguration` rather than resetting to unmuted at full volume. A non-default
  `appMuted` or `appVolume` is no longer discarded after the first full-screen ad.
- `audioVolume` is clamped before reaching the platform SDK on both platforms.

### Startup calls can no longer hang indefinitely

Native SDK initialization and the UMP consent-information update are now bounded. If the platform
SDK accepts the call and never invokes its callback, the operation fails with a diagnostic instead of
suspending forever.

A timed-out consent update reports `Failed`, and `canRequestAds` keeps whatever the last *completed*
refresh established. On a first run that is `false`, so a cold start still admits nothing while the
consent state is unknown. On a later run a previously granted `true` survives: a dropped network
round trip is not evidence that consent was withdrawn, and revoking admission on a blip would stop
ad serving until the next successful refresh without making consent any more correct.

Surfaces that wait for a person — the consent form, the privacy options form, and the ad inspector —
remain deliberately unbounded.

### Invalid configuration now fails at construction

Configuration objects validate their arguments in `init` and throw `IllegalArgumentException`
instead of carrying a nonsensical value into the platform SDK:

- `AdAppIds` and `AdUnitIds` reject blank `android` or `ios` values.
- `FullScreenAdOptions.audioVolume` must be finite and within `0.0f..1.0f`.
- App-open durations — `coldStartTimeout`, `cooldownBetweenShows`, and `minBackgroundDuration` —
  must be finite, and positive or non-negative respectively.

<Aside type="caution" title="Behaviour change">
These are constructor-time throws, so a value that previously degraded quietly at runtime now fails
where it is built. If any of these are assembled from remote config, a build flavour, or user input,
validate them before construction or wrap it — most affected code will not have a `try` around what
used to be a plain object construction.
</Aside>

### `AdLogger` is now configurable

`AdLogger` previously logged every message, at every level, unconditionally to the platform log
(`android.util.Log` / `NSLog`), with no way to quiet it in a release build or route it elsewhere.
Two new members, both additive and source-compatible:

- `AdLogger.minLevel: AdLogLevel` (default `Verbose`) — set to `Warn` or `Error` during app startup
  to drop routine diagnostic noise while keeping warnings and errors visible.
- `AdLogger.sink: AdLogSink?` — set to forward matching messages to Timber, `OSLog`, a crash
  reporter's breadcrumb trail, or any other destination. A sink **replaces** the platform log for
  messages at or above `minLevel`; it does not tee to both.

`AdLogLevel` is now `public` (previously `internal`), since a caller needs it to compare against
`minLevel` or implement `AdLogSink`.

### App ID verification is now configurable

A preflight check validates that the app ID configured in `AdConfig` agrees with the platform's declared ID (`Info.plist` on iOS, `AndroidManifest.xml` on Android) before touching UMP or GMA.

`AdAppIdVerification.policy` controls how the check behaves:

- `AppIdVerificationPolicy.FailWhenUnusable` (default) — fails initialization with `AdErrorCode.APP_ID_INVALID` only when the platform's native SDK cannot function with the declaration as found (a missing or blank `GADApplicationIdentifier` on iOS, which crashes native GMA). Android manifest mismatches and omissions log a warning and continue, because GMA Next-Gen initializes from `AdConfig.androidAppId` directly while UMP reads the manifest.
- `AppIdVerificationPolicy.Strict` — fails initialization immediately with `AdErrorCode.APP_ID_INVALID` on any missing or mismatched declaration. Recommended for new integrations, and the intended default starting in 3.0.0.
- `AppIdVerificationPolicy.WarnOnly` — logs a warning and proceeds for every finding, serving as an escape hatch if the platform declaration is resolved dynamically or via custom bundle packaging.

`AdAppIdVerification.policy` is a process-wide setting (like `AdLogger.sink`) and must be configured during app startup before the first `initialize()` call.


## What changed in 2.1.0?

A native-ad rendering release. The layout DSL had three hand-written renderers — Android views, iOS
UIKit, and the Compose `AdLayoutPreview` — and a property honoured by one and dropped by another
failed silently. This release resolves each of those decisions once, in common code, and fixes the
divergences that had accumulated.

### Rendering parity

- **The star rating renders the same everywhere.** It was a system `RatingBar` on Android (which
  cannot honour the node's `AdTextStyle` at all — no colour, font or size), a `"4.6 stars"` label on
  iOS, and `★ 4.6` in previews. All three now share one styled text rendering.
- **`AdModifier.padding` works on every node on iOS.** It was expressed as `UIView.layoutMargins`,
  which only a `UIStackView` reads, so padding on a label, image, media view or `Box` was accepted
  by the DSL and silently dropped. The iOS renderer now layers margin, size and decoration, padding,
  then content — the order Compose and the Android renderer already used.
- **`Box` and stack alignment on iOS.** All nine `contentAlignment` values are honoured instead of
  everything pinning top-start, `Row`/`Column` apply their main-axis arrangement, a `Row` places
  children at its `verticalAlignment` rather than stretching them, and a `Box` sizes to its largest
  child instead of a guessed one.
- **`weight` is proportional on iOS.** `weight(1f)` beside `weight(2f)` came out 1:1; weighted
  children now carry an exact ratio constraint and unweighted siblings hold their intrinsic size.
  `AdLayoutSize.Match` along a stack's main axis is treated as the same kind of claim, which is how
  Compose measures it.
- **`AdContentScale` is honoured for iOS media**, and **`AdDisplay.Gone` collapses its space** on
  both platforms.
- **Android text ellipsizes** when `maxLines` is set, instead of cutting mid-glyph.

### Policy and correctness

- **AdChoices is registered on Android.** The reserved slot was a placeholder that was never
  assigned to `NativeAdView.adChoicesView`, so the SDK drew its overlay in a default corner rather
  than where the layout put it.
- **Root corner radius and elevation are applied Compose-side on both platforms**, so a root shadow
  is no longer clipped away on Android.
- **`AdLayoutValidator` warns on a transparent layout root**, because iOS composites those onto the
  platform backdrop rather than the app's surface.

### Behaviour changes to be aware of

- **The call-to-action no longer inherits platform widget metrics.** It was an
  `android.widget.Button` and a `UIButton`, so its height came from the device theme's button style
  on Android — differing between manufacturers — and from `UIButtonConfiguration` on iOS. It is now
  built from a styled label on both platforms and sized as text plus its resolved insets, which
  gains a default vertical inset. Set `AdModifier.padding(...)` on the `callToAction` node to choose
  a different height.
- **A call-to-action's own modifier now takes precedence over its `AdButtonStyle`** for background
  and corner radius, in the same order the layout root uses. Previously the two overlapped with no
  stated precedence.
- **The star rating renders as text rather than a star widget** (see above), so layouts relying on
  the `RatingBar` appearance will look different.

### API

- **`AdTemplateColors`**, with `light` and `dark` built-ins, plus colour-parameterised
  `AdTemplates.compact(colors)`, `medium(colors)` and `feedCard(colors)`. The existing `AdTemplates`
  values are unchanged and still render the light palette; the overloads exist because the templates
  previously hardcoded a white card and were unusable in a dark UI. Purely additive — no existing
  binary signature changed.

### Previews

- `AdLayoutPreview` honours `AdDisplay.Invisible`, applies a node's own AdChoices size instead of
  overriding it, and no longer throws when a layout carries a non-positive `weight`.

## What changed in 1.1.1?

- **Cancelled banner loads no longer blank a live ad:** cancelling a banner load or refresh — a restarted effect, a resize, an explicit cancel — published `Idle`, which `BannerAdView` reads as "the ad is gone". A banner that was still loaded and on screen disappeared. The published state is now derived from the ad the controller actually still owns. See [Banner ads](/formats/banner/).
- **Ad state can no longer be resurrected after `clear()`:** the banner controller and native pool published their post-failure recovery state across two separate lock acquisitions, so a `clear()` landing in between was overwritten and the state reported `Loaded` for inventory that had just been released. Both now transition atomically.
- **Ads are no longer leaked when metadata reads fail:** if a platform response-info accessor threw after a successful load, the newly loaded banner or native batch was neither retained nor destroyed. Such ads are now torn down.
- **Ad SDK metadata is read on the main thread:** response and media information are captured during load rather than read back later from whichever dispatcher the caller used. This is historical context for the retired native-pool API; current native sessions publish media information with the slot state.
- **`testMode` warning no longer suppressed by consent debug IDs:** `AdDebugOptions.consentTestDeviceIds` configures UMP consent debugging only and never registers a GMA test device, so it no longer counts as evidence that test ads will be served. Configurations relying on it now correctly warn that live ads may be requested. See [Test ads and safety](/reference/compatibility/).
- **`AdPlacements` is genuinely immutable:** the placement list is copied at construction, so it can no longer be mutated behind Compose's back after being marked `@Immutable`.
