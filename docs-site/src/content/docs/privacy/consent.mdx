## How does UMP consent work in AdMob CMP?

Consent is integrated into initialisation rather than bolted beside
it, which makes requesting ads before consent impossible by
construction. The User Messaging Platform (UMP) SDK is what presents the
consent form on both platforms, but the orchestration — gathering
consent, presenting the form if required, then starting Mobile Ads — is
the library's responsibility. The result is a single
`gatherConsentAndInitialize` call that handles the whole flow.

A naive integration
that runs `MobileAds.initialize()` and then calls `requestConsentInfoUpdate`
admits a window of time during which ad requests are sent to a user
who has not been asked for consent. AdMob policy treats any request to a user who has not
been prompted in applicable regions as a violation. The library's init order closes this
window by design.

```kotlin
adManager.gatherConsentAndInitialize(
    AdConfig(
        appIds = AdAppIds(
            android = "ca-app-pub-…",
            ios = "ca-app-pub-…",
        )
    )
)
```

`ConsentStatus` is a sealed interface with five cases:

| `ConsentStatus` | Meaning |
|---|---|
| `Unknown` | Not determined yet. |
| `Required` | A form must be shown. |
| `Obtained` | The user answered — which does not necessarily mean they consented to personalised ads. |
| `NotRequired` | Regulation does not require consent for this user. |
| `Failed(error)` | The consent-info update failed; the error is attached. |

A practical note on consent state: there are three distinct concepts at play.
1. The **return value** of a suspending call describes the outcome of that specific attempted operation.
2. `consent.status` is the **shared published state**. A rejected busy call leaves this unchanged.
3. `consent.canRequestAds` determines **consent admission**. Actual ad loading also requires manager readiness.

When an operation returns `Failed(error)`, the error is a regular
`AdError` carrying standard fields — `code`,
`message`, `domain`, `responseInfo`. The most common cause is a
network failure, which is a
transient condition. A persistent `Failed`
state usually points to a misconfigured AdMob app ID.

Before you show a person an error, check `canRequestAds`. A failed refresh does not revoke
consent: UMP keeps whatever the last completed refresh established, so
`consent.canRequestAds` may still be `true` and ads may still serve while
an operation failed. This is [what Google's own guidance recommends
checking](https://developers.google.com/admob/android/privacy).

If an action fails because a form is already showing or an update is in progress, wait for the existing operation to finish before retrying if the action is still needed. Do not implement an automatic retry loop: a duplicate tap should not cause another form to open after dismissal.

### Handling errors in 2.2.0

```kotlin
import dev.avinya.ads.AdManager
import dev.avinya.ads.AdConfig
import dev.avinya.ads.ConsentStatus

suspend fun startConsentFlow(adManager: AdManager, config: AdConfig) {
    val result = adManager.consent.gatherConsent(config)

    if (result is ConsentStatus.Failed) {
        if (adManager.consent.canRequestAds.value) {
            // Refresh failed, but a previous session's choice still permits ads.
        } else {
            // A real consent problem worth surfacing. Note that 2.2.0 has no dedicated
            // busy-error constant, and not every failed native refresh is guaranteed
            // to return Failed.
        }
    }
}
```

<Aside type="note" title="New in 2.3.0 — unavailable in 2.2.0">
The following demonstrates handling the busy error introduced in 2.3.0. This code branches on the awaited operation result, never `consent.status.value`. A `CONSENT_OPERATION_IN_PROGRESS` error is returned to the declined caller as a declined concurrent request, and explicitly is not published to the status flow. The same handling applies to `requestConsentInfoUpdate(config)`. These examples are alternatives for different versions, do not call both sequentially.

```kotlin
import dev.avinya.ads.AdErrorCode
import dev.avinya.ads.AdManager
import dev.avinya.ads.AdConfig
import dev.avinya.ads.ConsentStatus

suspend fun startConsentFlow(adManager: AdManager, config: AdConfig) {
    val result = adManager.consent.gatherConsent(config)

    if (result is ConsentStatus.Failed) {
        if (result.error.code == AdErrorCode.CONSENT_OPERATION_IN_PROGRESS) {
            // Another consent operation is already running.
        } else if (adManager.consent.canRequestAds.value) {
            // Refresh failed, but a previous session's choice still permits ads.
        } else {
            // A real consent problem worth surfacing.
        }
    }
}
```

Additionally, in 2.3.0, `error.domain` is improved on consent errors to distinguish the platform the numeric `code` came from. Android's `FormError.ErrorCode` and iOS's `UMPRequestErrorCode` both use `1..4` with different meanings, so never branch on a bare numeric consent code without it.
</Aside>

## Which ConsentMode should I use?

```kotlin
adManager.initialize(config, ConsentMode.GatherBeforeInitialize)
```

| `ConsentMode` | Behaviour |
|---|---|
| `GatherBeforeInitialize` | Request UMP consent info, present the form if required, then initialise Mobile Ads. Recommended default. |
| `InitializeOnlyIfAlreadyAllowed` | No form presented. Initialise Mobile Ads only if consent already permits requests; otherwise status becomes `ConsentRequired`. |
| `SkipConsent` | Bypass UMP consent checks entirely. For non-EEA/UK target regions or custom consent management. |

`gatherConsentAndInitialize(config)` is a convenience extension for `GatherBeforeInitialize` with
the ergonomics of a single call and is the recommended default. Use
`InitializeOnlyIfAlreadyAllowed` when the application drives consent and platform prompts
itself — for instance to sequence App Tracking Transparency (ATT)
between consent gathering and Mobile Ads initialisation on iOS. Do **not** substitute
`SkipConsent` in that sequence, because skipping ignores future UMP revocation.
`SkipConsent` is intended strictly for applications that have no UMP obligations.

The three modes accommodate three main usage patterns:
- Applications presenting the UMP form as their only consent UI use `GatherBeforeInitialize`.
- Applications that drive their own consent workflow (or sequence iOS ATT in a pre-initialisation hook) use `InitializeOnlyIfAlreadyAllowed`.
- Applications with no GDPR/UK consent obligations use `SkipConsent`.

## What is canRequestAds and how does it gate ad requests?

```kotlin
val consentStatus by adManager.consent.status.collectAsState()
val canRequestAds by adManager.consent.canRequestAds.collectAsState()
```

`canRequestAds` is a `StateFlow<Boolean>` exposed on `adManager.consent`.
The SDK refuses ad requests with `AdErrorCode.CONSENT_REQUIRED`
until `canRequestAds` is `true`, unless the mode is `ConsentMode.SkipConsent`. Before
initialisation succeeds, loads fail fast with
`AdErrorCode.SDK_NOT_READY`. In both cases, **nothing reaches the
network** — a failed load here indicates the consent or readiness gate is active. The
[troubleshooting guide](/reference/troubleshooting/) covers the full
symptom table.

A key point: `ConsentStatus.Obtained` means the
user completed the UMP form, not that they consented to ad personalisation or request serving. Branch on
`canRequestAds`, never solely on `Obtained`.

`canRequestAds` is a derived state reflecting UMP consent rules. If an application requires additional publisher-side policy conditions (such as a custom in-app opt-out, subscription state, or age-gating), manage that as a separate application-level boolean check:

```kotlin
val canServeAds = canRequestAds && userPublisherPolicyAllowed
```

Do not attempt to pass custom application flags into `canRequestAds`. Keep publisher policy gating distinct from SDK UMP state.

## What is the canonical production startup order?

For production applications — especially multiplatform apps on iOS — the recommended initialisation sequence is:

1. **Gather UMP consent**: Call `adManager.consent.gatherConsent(config)` or `requestConsentInfoUpdate(config)`.
2. **Execute pre-initialisation hooks**: On iOS, run any configured `AdInitializationHook` instances during the `BeforeMobileAdsInitialize` phase (for example, to trigger `adManager.tracking.requestAuthorization()` if ATT tracking is configured).
3. **Initialise Mobile Ads**: Call `adManager.initialize(config, ConsentMode.InitializeOnlyIfAlreadyAllowed)` or `adManager.gatherConsentAndInitialize(config)`.
4. **Load ads**: Request ad loads only after `adManager.status` transitions to `AdManagerStatus.Ready`.

## When should I show a Privacy Settings button?

```kotlin
val privacyRequirement by adManager.consent.privacyOptionsRequirementStatus.collectAsState()

if (privacyRequirement == PrivacyOptionsRequirementStatus.Required) {
    Button(onClick = { scope.launch { adManager.consent.showPrivacyOptions() } }) {
        Text("Privacy Settings")
    }
}
```

This provides the GDPR re-consent affordance.
`PrivacyOptionsRequirementStatus` evaluates to `Unknown`, `Required`, or
`NotRequired`. `showPrivacyOptions()` returns a `Boolean`
indicating whether the form was presented.

<Aside type="caution">
Do **not** gate this button on `ConsentStatus.Obtained`. Users who
previously declined or restricted consent must still be able to reopen the privacy options form. Gating
on `Obtained` hides the entry point from users who need to modify their choices.
</Aside>

`showPrivacyOptions()` is suspending and presents the form or returns `false` if no management form is available.

Showing the button only when `privacyOptionsRequirementStatus` is
`Required` aligns UI with platform requirements: the button appears when required by regulation and remains hidden when not applicable.

## How do I test the EEA consent flow?

`GlobalRequestConfiguration(testDeviceIds = ...)` registers **GMA
test devices** for serving test ads. **UMP
consent-form test devices** are configured separately via
`AdDebugOptions.consentTestDeviceIds`. To test the EEA consent form flow on a
physical device:

```kotlin
adManager.gatherConsentAndInitialize(
    AdConfig(
        appIds = AdAppIds(android = "ca-app-pub-…", ios = "ca-app-pub-…"),
        debugOptions = AdDebugOptions(
            testMode = true,
            consentDebugGeography = ConsentDebugGeography.Eea,
            consentTestDeviceIds = listOf("YOUR-DEVICE-HASH"),
        ),
        globalRequestConfiguration = GlobalRequestConfiguration(
            testDeviceIds = listOf("YOUR-DEVICE-HASH"),
        ),
    )
)
```

`ConsentDebugGeography` can be `Disabled`, `Eea`, or `NotEea`. Debug
settings apply only when `testMode = true`. The device hash is
printed to logcat or Xcode console output on the first request from an unregistered test device. The [test safety guide](/advanced/test-safety/) covers the
`testMode` versus `strictTestMode` distinction in detail.

The device hash is an identifier generated by the UMP SDK. It is stable for the local installation and rotates if app data is cleared.

## How do I reset consent during development?

```kotlin
scope.launch { adManager.consent.resetConsentForDebug() }
```

`resetConsentForDebug` is a debug-only utility that clears cached UMP consent decisions so the form re-prompts on the next gather call. It is designed solely for development testing and must not be called in production releases.

## How do I refresh consent state without showing a form?

```kotlin
scope.launch { adManager.consent.requestConsentInfoUpdate(config) }
```

`requestConsentInfoUpdate` updates `status`, `canRequestAds`, and
`privacyOptionsRequirementStatus` without presenting a UI form. This is suitable for invocation when opening a settings screen or resuming the application. In contrast, `gatherConsent(config)` presents the form if required.

`requestConsentInfoUpdate` is a suspending call that completes after updating state with the UMP backend. Because it presents no UI, it can safely run in a `LaunchedEffect` or background coroutine.
